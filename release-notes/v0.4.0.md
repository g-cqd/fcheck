# fcheck 0.4.0 (from 0.3.0)

`leak-on-exit` follows calls paired on a receiver or an argument, `cut-then-decode` reads the decodes that return nil,
and a documented configuration no longer fails (analyzerkit roadmap 0062, 0063, 0066). analyzerkit is still `0a13bbf`.

## Exit codes

A resource without `negativeIsInvalid`, as the README's own example writes it, exited 78; it is read as false.

## Report

The explanations of `leak-on-exit` and `cut-then-decode` describe the new shapes (`fcheck explain`, SARIF's help text).

## Configuration

A resource may say `"holds": "receiver"` (`x.begin()` … `x.end()`, method names) or `"firstArgument"`
(`lock(x, …)` … `unlock(x, …)`); `"result"`, the default, is what every resource did before.

## Findings that may appear

- `leak-on-exit`, built in: `beginConfiguration`/`commitConfiguration` and `lockForConfiguration`/`unlockForConfiguration`
  on a receiver, `CVPixelBufferLockBaseAddress`/`CVPixelBufferUnlockBaseAddress` on the first argument, when a path out
  (a throw, a return) skips the release. Passing the receiver on does not end the pair. Followed only when the opening
  call is a statement of its own and the receiver a simple name. On maintastic: `CaptureActor.configureSessionIfNeeded()`
  (QR scanner), and nothing for its other fifteen such sites.
- `cut-then-decode`: `String(data:encoding: .utf8)`, `String(bytes:encoding: .utf8)` and `String(<cut utf8 or utf16
  view>)` of bytes cut at a count. None on maintastic or the family's repositories.
